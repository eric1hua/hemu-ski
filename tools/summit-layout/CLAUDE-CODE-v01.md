# 云霄峰山顶重建：给 Claude Code 的施工说明 v01

## 要完成的事

在 Hemu Ski 的**游戏**中，根据本目录的 `summit-layout-v01.png` 和 Cowart
「吉克普林云霄峰地形重建」两张已标注照片，调整 6、7 号索道上站附近的
局部地形，并放置 `object 1` 至 `object 7` 共七个可独立替换的几何占位模型。
先实现地形、站位、通路和碰撞，正式建筑模型以后再做。

读取并遵守项目 `AGENTS.md`。当前工作区已有其他修改，先查看 diff，保留它们，
在现有代码上衔接。此次设计资料本身没有改动游戏、地形或地图编辑器。
不要调用收费模型或图像 API。不要把 production 工具加入发布入口。

## 阅读顺序和事实边界

1. `summit-layout-v01.png`：上半部是关系示意与体块清单，下半部两张照片是依据。
2. `reference-pins-v01.json`：Cowart 原箭头的端点、原图归一化坐标、图片裁剪信息。
3. `layout-v01.json`：七个稳定 ID、建议几何体、假定尺寸和当前游戏站点参考。
4. 本文的施工与验收要求。

编号沿用用户原标注。对象名称只描述可见形态，不代表已核实的建筑用途。
**7 个 object 不包含两座索道上站，也不包含 object 5 附近的高通信杆。**

关系图的 UV 是从斜拍航拍图的像平面投影得到的，不是摄影测量后的地面坐标。
照片存在透视、高差和遮挡，所以不能把 UV 直接乘站距当成最终世界坐标。
图上的地形边界也是拟建关系示意，不是测得的等高线或崖线。
所有建议尺寸只是可调的体块起点。两图拍摄方向不同，不能直接按屏幕左右摆放。
`object 6` 只有一张图有明确标注，它在关系图中的位置是**待复核的假设点**。
`worldPosition`、`yawRadians` 故意留空，避免把未确定的值当成事实。

交付前，画布中另出现了标为 `object7` 的夏季建筑近照：
`canvas/pages/ApwypO47DueJozzQFxZIw/assets/asset--2129279090.jpg`，
图片 shape ID 为 `shape:4sir-ZVUN89p8Go6VaQiW`。
它可补充 object 7 的多片双坡屋顶、木墙和正面开口形态；站位仍以两张冬季
总览为依据，不从这张近照推算绝对位置。v01 施工图仍采用简化盒体占位。

它们在当前数据中相距约 43.65 m。这是**游戏现有数据**，不是照片中的实测站距；
高度也不是重建目标。开始前重新读取当前存档，数据若已变动，以新数据为准。

- `src/world/props.js` 的 `liftStations()` 会处理共享端点的站房偏移。
  用它得到实际站房中心，用当前高度场辨别上站，不要只假定 points 的第一或最后点。
- 保留两条现有索道的 ID、上下站关系、缆线和乘坐功能。优先保持上站位置，
  通过局部地形与周边站位拟合照片。不要为了把示意图摆成一样而整体挪动索道。
- 以实际 6 号上站为局部原点，指向实际 7 号上站为 U。另一轴的正负必须通过
  两张照片的木屋、雕塑和坡边建筑对照选择；图的 V 并不等于世界北向。
- 使用航拍图检查绕站顺序和分布；反向图检查雪包、遮挡、崖侧和前后高差。
  建立两个可重复的调试相机，分别匹配两张参考的观察方向。
- 位置、yaw、地面目标高度及碰撞范围集中在一份配置中，便于调整。
  先做可审阅的 blockout；不要伪造精确经纬度、实测朝向或高程。

## 地形施工

目标是复现可辨识的地形关系，不是把山顶抹成一个大平台：

- **A 站区与通行雪台**：两站间连通，站房与建筑脚下各有局部平整支撑；
  连接区保留柔和起伏。先按 6–10 m 的可调走滑廊道试摆，避免雕塑和模型挡路。
- **B object 1 周边圆钝雪包**：保留圆滑凸起和可绕行侧坡；不要把帐篷简单
  放在与两站完全等高的大平面上。隆起幅度要看两视角校准，未指定真实高差。
- **C 通往 object 4 的山脊延伸**：从站区向外逐渐收窄，形成连接，而非把
  object 4 平移进中央广场。连线与相对高程以照片为准，关系图不表示爬升量。
- **D 崖侧与 object 7 的雪肩**：区分外侧陡坡和内侧可通行连接；保留边坡
  起伏、局部雪台和独立建筑落脚点，避免凭一张图挖出穿地的垂直洞。

把改动限制在山顶局部，边界平滑接回原 DEM；保留远山、山谷和其他雪道。
先记录基线与修改范围，保留原始高度场和现有地图编辑内容。

游戏的基础网格步长为 8 m，山脊/台阶可能小于一个网格。几何渲染变细不等于
地形数据新增真实细节。若需要细尺度地形修正，使用渲染、物理、落地采样都
共享的局部高度修正，并明确它与地图编辑器存档的叠加顺序。
不要只堆可见雪块而让玩家仍与旧地面碰撞，也不要为山脊改动清空全图存档。

## 接入现有代码的建议

开始时重新看相关代码；以下是本次核对时的结构，不要求照搬文件设计：

- `src/main.js`：游戏 `loadWorld('', { edits: ... })` 后经过 `raiseBanks()` 得到
  最终 `detail`。地形修正要在地形 mesh、站点、物体和碰撞创建前完成，并确保
  `heightAt()` 与实际渲染相符；雪道边缘 bank 不应穿入建筑支撑面。
- `src/world/data.js`：目前 Places 只注册大厅、温泉和车辆。`applyPlaces()`
  会过滤未注册 ID，**仅向 edits.places 写七个 ID 不会让它们自动出现**。
- 新增可替换的占位物体模块，例如 `src/world/summit-landmarks.js`，为每个 ID
  建立独立 `THREE.Group`，底心为 pivot，朝向约定沿用 Places 的 yaw 0 → +z。
  几何占位和未来 `modelUrl` 共享同一个父 Group；替换模型时保留站位与碰撞配置。
- 把七个 ID 注册进 Places / `placeOf()` 流程，并在
  `tools/map-editor/objects-view.js` 的物体信息与绘制中添加相应 footprint。
  让 Objects 工具能选择、移动、旋转和保存这七个点位。跟随编辑器当前未提交实现。
- 游戏的 snowboard、车辆、飞行器共用障碍数据：把需要阻挡的体块 footprint
  接入对应 obstacles，包含正确的 `top`。木框的空洞应可穿过，别用整块盒子
  把洞堵死；细杆可用分开的窄碰撞体。
- 渲染沿用现有 `makeToon` / 描边风格即可，占位阶段每个物体可用编号标签。
  正式模型之后在资产 lab 生产，再交接至 `public/models/<name>/`。
- 若新配置要供游戏读取，放 `src/` 或 `public/`。`tools/summit-layout/`
  是施工资料，游戏不得从这里导入。不要增加 build HTML 入口。
- diorama 目前独立读取 `public/data/diorama/`。这次只改游戏山顶，
  不要声称游戏编辑存档会自动同步到 diorama。

## 完成后的检查与交付

1. 执行 `npm run build` 与 `npm test`，报告真实结果。
2. 在游戏中使用两台对应参考视角的相机，保存两张编号截图；另保存一张
   高处俯视截图。确认恰好七个地标，站房没有重复，object 6 标明待复核。
3. 从两站下客位置分别走到中央区、绕过 object 1，走到 object 4 / 7 的连接处。
   观察无悬空、陷地、通路被模型堵塞、可见地面与碰撞高度不一致的问题。
4. 实际乘坐 6、7 号索道上山，核对站房、缆线、下客位置和云霄峰道起点。
   原有地图编辑存档可继续加载；在 Objects 工具移动并保存一个占位物后，
   刷新游戏能读取该站位。
5. 区分报告：构建/测试是 checked；实际截图与跑过的交互是 observed；
   用户明确接受才是 approved。提交可审阅的 blockout 截图，不把草案标成已批准。

本阶段交付应是可调整、可替换的七物体山顶 blockout。正式资产生成与替换
是下一阶段，收费调用需要用户逐次明确同意。
